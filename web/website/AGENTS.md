
# AGENTS.md — APSco Storefront

این فایل شامل قوانین و استانداردهای الزامی برای توسعه وب‌سایت فروشگاهی APSco است.

تمام دستورالعمل‌های این فایل باید هنگام بررسی، ایجاد، ویرایش و توسعه کد رعایت شوند.

---

# 1. قوانین کلی توسعه

- کدهای جدید باید تا حد امکان با سبک کدنویسی، ساختار و الگوهای موجود در پروژه هماهنگ باشند.
- قبل از پیاده‌سازی هر قابلیت، ابتدا کدها و کامپوننت‌های مرتبط موجود در پروژه را بررسی کن.
- از ساخت کامپوننت‌ها، توابع و منطق‌های تکراری خودداری کن.
- اگر کامپوننت یا قابلیت مشابهی از قبل وجود دارد، از همان استفاده کن.
- بدون هماهنگی با کاربر هیچ پکیج یا وابستگی جدیدی نصب نکن.
- کدهای فعلی پروژه را بدون دلیل منطقی بازنویسی یا تغییر نده.
- فقط فایل‌ها و بخش‌هایی را تغییر بده که برای انجام درخواست ضروری هستند.
- از تغییر ساختار معماری پروژه بدون هماهنگی خودداری کن.
- هیچ کامنتی داخل کدها قرار نده؛ مگر اینکه کاربر صریحاً درخواست کرده باشد.
- کدها باید تمیز، خوانا، استاندارد و مرتب باشند.
- از پیچیده‌سازی غیرضروری کدها خودداری کن.

# 2. بررسی درخواست قبل از پیاده‌سازی

- قبل از شروع توسعه، درخواست کاربر را به‌دقت بررسی کن.
- اگر اطلاعات کافی برای پیاده‌سازی وجود ندارد، ابتدا سؤال بپرس.
- در صورت وجود ابهام در منطق تجاری، ساختار داده، API یا رفتار مورد انتظار، خودسرانه تصمیم نگیر.
- هیچ API، endpoint، فیلد، قابلیت یا رفتار تجاری را بدون اطلاعات معتبر فرض نکن.
- اگر چند روش برای پیاده‌سازی وجود دارد و انتخاب روش روی معماری پروژه تأثیر می‌گذارد، ابتدا موضوع را با کاربر هماهنگ کن.
- از پیاده‌سازی قابلیت‌هایی که کاربر درخواست نکرده است خودداری کن.

# 3. معماری پروژه

معماری پروژه به شکلی طراحی شده که مسئولیت فایل‌های داخل `app` و `features` از یکدیگر جدا باشد.

## App

پوشه `app` مسئول مدیریت Routeها و فراخوانی API است.

قوانین:

- صفحات معمولی داخل `app` نباید مستقیماً رابط کاربری صفحه را پیاده‌سازی کنند.
- مسئولیت اصلی صفحات، فراخوانی API و دریافت اطلاعات موردنیاز است.
- اطلاعات دریافت‌شده باید به کامپوننت اصلی صفحه در `features` ارسال شوند.
- از قرار دادن منطق رابط کاربری و ساختارهای JSX مربوط به صفحات در این بخش خودداری کن.
- فایل‌های `page.tsx` باید تا حد امکان سبک و متمرکز بر مدیریت داده باشند.

مثال:

```tsx
import HomePage from "@/features/Home/HomePage";

export default async function Page() {
    const data = await getHomeData();

    return <HomePage data={data} />;
}
```

## Features

پوشه `features` مسئول پیاده‌سازی قابلیت‌ها و صفحات اصلی سایت است.

قوانین:

- کامپوننت اصلی هر صفحه باید داخل Feature مربوط به خودش قرار بگیرد.
- منطق و رابط کاربری اختصاصی هر صفحه باید در همان Feature مدیریت شود.
- کامپوننت‌هایی که فقط در یک صفحه استفاده می‌شوند، باید در ساختار داخلی همان Feature نگهداری شوند.
- از انتقال بی‌دلیل کامپوننت‌های اختصاصی به پوشه کامپوننت‌های عمومی خودداری کن.

# 4. قوانین ساختار و محل قرارگیری کامپوننت‌ها

کامپوننت‌ها به دو گروه اصلی تقسیم می‌شوند:

1. کامپوننت‌های عمومی و مشترک پروژه
2. کامپوننت‌های اختصاصی هر صفحه یا Feature

## کامپوننت‌های اختصاصی Feature

اگر کامپوننتی فقط در یک صفحه استفاده می‌شود، باید داخل پوشه کامپوننت‌های همان Feature قرار بگیرد.

مثال:

```text
features/
└── Products/
    ├── ProductsPage.tsx
    └── components/
        ├── ProductFilters.tsx
        └── ProductList.tsx
```

## کامپوننت‌های مشترک

اگر کامپوننتی در بیش از یک صفحه استفاده شد، ابتدا باید بررسی شود که آیا قابلیت انتقال به بخش عمومی پروژه را دارد یا خیر.

در صورت عمومی بودن، باید به محل مناسب در پوشه `components` منتقل شود.

قبل از انتقال، موارد زیر را بررسی کن:

- آیا کامپوننت واقعاً عمومی است؟
- آیا به منطق اختصاصی یک Feature وابستگی دارد؟
- آیا می‌توان آن را بدون وابستگی به یک صفحه خاص استفاده کرد؟
- آیا کامپوننت مشابهی در پروژه وجود دارد؟

## کامپوننت‌های UI

کامپوننت‌های پایه رابط کاربری مانند موارد زیر باید در بخش `Ui` قرار بگیرند:

- Button
- Input
- Select
- Checkbox
- Radio
- Switch
- سایر کامپوننت‌های پایه رابط کاربری

برای مثال، اگر کامپوننت `BaseButton` از قبل وجود دارد، برای ساخت دکمه جدید باید از همان استفاده شود.

برای دکمه‌های جدید، کامپوننت جداگانه نساز؛ مگر اینکه واقعاً ماهیت و رفتار متفاوتی داشته باشند و ساخت آن با الگوی موجود امکان‌پذیر نباشد.

## کامپوننت‌های Shared

کامپوننت‌های مشترک باید با توجه به مسئولیتشان در بخش مناسب قرار بگیرند.

این بخش شامل دو گروه مهم است:

- کامپوننت‌های عمومی و مستقل از Layout صفحات
- کامپوننت‌های مربوط به Layout مانند Header، Footer و سایر اجزای اصلی چیدمان

قبل از ایجاد پوشه یا ساختار جدید، ابتدا ساختار فعلی `components` را بررسی کن.

## نکته مهم درباره ایجاد فایل‌ها

ممکن است در ابتدای توسعه، برخی فایل‌ها و پوشه‌ها توسط اعضای تیم به‌صورت دستی ایجاد شوند.

- فایل‌ها و پوشه‌های موجود را بدون بررسی تغییر نده.
- از ساخت فایل‌های تکراری خودداری کن.
- قبل از ایجاد فایل جدید، وجود فایل یا قابلیت مشابه را بررسی کن.
- از ساخت پوشه‌های خالی و بدون کاربرد خودداری کن.

# 5. استانداردهای فرمت و قالب‌بندی کد

یکی از مهم‌ترین قوانین پروژه، حفظ نظم و یکپارچگی ظاهری کدها است.

کدهای جدید باید از نظر فاصله‌گذاری، تورفتگی، چینش JSX و نحوه نوشتن کلاس‌های Tailwind با الگوی موجود پروژه هماهنگ باشند.

## تورفتگی و چینش کد

- تورفتگی‌ها باید منظم و یکسان باشند.
- کدهای چندخطی باید ساختار مشخص و خوانایی داشته باشند.
- از شکستن بی‌دلیل خطوط خودداری کن.
- چینش props در کامپوننت‌ها باید منظم باشد.
- ساختار JSX باید خوانا و مرتب باشد.

## نحوه نوشتن کلاس‌های Tailwind

در صورتی که تعداد کلاس‌های Tailwind زیاد شد و نیاز به شکستن آن‌ها در چند خط بود، خطوط بعدی باید دقیقاً از زیر اولین کلاس شروع شوند.

مثال صحیح:

```tsx
<div
    className="flex flex-col items-center justify-between gap-y-5
               w-full rounded-xl border border-primary-20 bg-bg p-5
               shadow-sm"
>
```

مثال نادرست:

```tsx
<div
    className="flex flex-col items-center justify-between gap-y-5
    w-full rounded-xl border border-primary-20 bg-bg p-5
    shadow-sm"
>
```

قانون مهم:

- کلاس‌های خطوط بعدی باید با فاصله مناسب و دقیقاً زیر شروع اولین کلاس قرار بگیرند.
- این قانون برای تمام کلاس‌های چندخطی JSX رعایت شود.
- ترتیب و نحوه دسته‌بندی کلاس‌ها باید با الگوی موجود پروژه هماهنگ باشد.
- از قالب‌بندی نامنظم و پراکنده کلاس‌ها خودداری کن.

# 6. استانداردهای React و TypeScript

- از TypeScript مطابق ساختار فعلی پروژه استفاده کن.
- برای props کامپوننت‌ها type مشخص تعریف کن.
- از استفاده غیرضروری از `any` خودداری کن.
- از تکرار typeها و interfaceهای مشابه جلوگیری کن.
- قبل از تعریف type جدید، typeهای موجود را بررسی کن.
- کامپوننت‌ها باید مسئولیت مشخص و محدودی داشته باشند.
- از ایجاد کامپوننت‌های بیش‌ازحد بزرگ خودداری کن.
- منطق مشترک را در صورت نیاز به توابع یا Hookهای مناسب منتقل کن.
- از استفاده غیرضروری از `useEffect` خودداری کن.
- از `"use client"` فقط در مواقع ضروری استفاده کن.
- تا جای ممکن از قابلیت Server Components در Next.js استفاده کن.
- از الگوهای موجود پروژه برای مدیریت State و داده‌ها پیروی کن.

# 7. استانداردهای رابط کاربری

- طراحی باید مدرن، حرفه‌ای، مینیمال و مناسب یک فروشگاه اینترنتی واقعی باشد.
- از ساخت باکس‌ها و کارت‌های تکراری و بدون هدف خودداری کن.
- سلسله‌مراتب بصری صفحات باید مشخص باشد.
- طراحی باید Responsive باشد.
- رفتار صفحات در موبایل، تبلت و دسکتاپ بررسی شود.
- از کامپوننت‌های موجود برای عناصر تکراری رابط کاربری استفاده کن.
- وضعیت‌های Loading، Error، Empty و Success در صورت نیاز در نظر گرفته شوند.
- از فونت‌ها و الگوهای طراحی موجود پروژه استفاده کن.
- پشتیبانی از زبان فارسی و انگلیسی و جهت‌های RTL و LTR رعایت شود.
- پنل مدیریت خارج از محدوده این دستورالعمل است.

# 8. ارتباط با API و مدیریت داده

- فراخوانی API در صفحات معمولی باید مطابق معماری پروژه در `app` انجام شود.
- اطلاعات دریافت‌شده باید به کامپوننت‌های مربوط در `features` ارسال شوند.
- از پیاده‌سازی مجدد منطق دریافت اطلاعات در بخش‌های مختلف بدون ضرورت خودداری کن.
- از ساخت داده‌های ساختگی برای جایگزینی API واقعی بدون هماهنگی خودداری کن.
- ساختار Response و Request باید بر اساس اطلاعات واقعی API باشد.
- مدیریت خطاها باید مطابق الگوی موجود پروژه انجام شود.
- اطلاعات حساس و Tokenها نباید مستقیماً در کد قرار بگیرند.

# 9. قوانین مربوط به توسعه قابلیت‌های فروشگاه

- ساختار دسته‌بندی محصولات باید قابل توسعه باشد.
- محصولات می‌توانند در دسته‌بندی‌های مختلف و متنوع قرار بگیرند.
- منطق موجودی و تنوع محصولات باید مطابق ساختار داده واقعی پروژه پیاده‌سازی شود.
- خرید مهمان مجاز نیست و ثبت‌نام برای خرید الزامی است.
- خرید کاربران خارجی باید مطابق فرآیند تأیید قیمت نهایی انجام شود.
- در مواردی که قوانین تجاری هنوز مشخص نشده‌اند، هیچ تصمیمی را خودسرانه پیاده‌سازی نکن.
- قابلیت مقایسه محصولات در محدوده فعلی پروژه نیست.
- قابلیت‌های هوش مصنوعی فعلاً خارج از محدوده توسعه هستند.
- جزئیات ارسال محصولات داخل ایران و پرداخت آنلاین کاربران خارجی نباید بدون مشخص شدن قوانین نهایی فرض شوند.

# 10. امنیت و کیفیت

- اطلاعات حساس را در کدهای پروژه قرار نده.
- از متغیرهای محیطی برای اطلاعات محرمانه استفاده کن.
- ورودی‌های کاربران را معتبر فرض نکن.
- خطاها را به‌شکل کنترل‌شده مدیریت کن.
- از دست‌کاری غیرضروری تنظیمات پروژه خودداری کن.
- تنظیمات TypeScript، ESLint و Next.js را برای پنهان کردن خطاها تغییر نده.

# 11. روند انجام وظایف

برای انجام هر درخواست، مراحل زیر را رعایت کن:

1. ابتدا درخواست را به‌دقت بررسی کن.
2. فایل‌ها و کامپوننت‌های مرتبط را پیدا کن.
3. معماری و الگوهای فعلی پروژه را بررسی کن.
4. در صورت وجود ابهام، قبل از پیاده‌سازی سؤال بپرس.
5. کامپوننت‌ها و توابع موجود را برای استفاده مجدد بررسی کن.
6. فقط تغییرات ضروری را انجام بده.
7. از تغییر فایل‌های نامرتبط خودداری کن.
8. پس از توسعه، کدها را از نظر ساختار، کیفیت و سازگاری بررسی کن.
9. در صورت امکان، دستورات بررسی و Build پروژه را اجرا کن.
10. در پایان، تغییرات انجام‌شده و فایل‌های تغییرکرده را به‌صورت خلاصه توضیح بده.

- اگر کاربر صریحاً قانونی را برای یک درخواست تغییر داد، همان دستور جدید را برای آن درخواست در نظر بگیر.
- هیچ تغییری را بدون نیاز واقعی انجام نده.
- هدف اصلی، توسعه کدی تمیز، استاندارد، قابل نگهداری و هماهنگ با کل پروژه است.
